Methodology

Development Approach

A systematic, AI-augmented workflow combining requirements analysis, system design prompting, phase-based development, and rigorous testing.

Phase 0: Requirements & System Design

The project began with comprehensive requirement analysis, followed by Claude serving as a system designer. A detailed design prompt was provided to ensure architectural coherence across all layers:

Initial Design Prompt (Abbreviated):

Objective: AI-powered operations intelligence platform for organizing operational information, analyzing incidents, intelligent search, and insight generation.

User Capabilities:
  • Workspace/project creation for information organization
  • Data upload: Logs, CSV, PDFs, TXT, JSON
  • Semantic search across all data
  • AI summarization & incident analysis
  • Dashboard with activity feed, insights, analytics
  • Role-based access (Owner, Admin, User)
Initial Tech Stack: Next.js, Tailwind, TypeScript, Neon DB with pgvector, Prisma ORM, OpenRouter (free tier), Clerk authentication.
Key Design Clarifications:
  • MVP Scope: Focus on OpenRouter for cost efficiency; skip alert system & WebSockets; use cached strategy for offline awareness
  • Architecture: All database actions in API routes (no frontend queries); role-based access via Clerk; rate limiting on all user-facing endpoints
  • Data Pipeline: File upload → Object storage (Supabase R2) → Metadata in Neon → Chunking strategy → Embedding generation → pgvector indexing → Semantic search
  • Security-First: Authentication on every API route, input validation, magic byte file verification, SQL injection prevention via Prisma
  • Alerting & Notifications: Deferred to Phase N; currently using NextAuth + Clerk with token-based session management

Design Principles

The platform follows a modern AI-native SaaS aesthetic inspired by Linear, Notion, Vercel, and Stripe:

  • Minimalism: Clean spacing, structured information hierarchy, high readability
  • Bento UI Layouts: Card-based component arrangement for dashboard modularity
  • Editorial Typography: Strong visual hierarchy with clear distinction between headings, body, and metadata
  • Dark Mode Primary: Default dark interface (zinc-950 backgrounds) with high contrast for accessibility
  • Subtle Glassmorphism: Applied only to modals, command palettes, and floating panels (avoid overuse)
  • Avoid: Neo-Brutalism, Claymorphism, Neumorphism, excessive gradients, decorative elements
  • Feel: Professional, intelligent, trustworthy, data-focused

Development Workflow

Each feature phase follows a structured prompt-driven approach:

  1. Phase Planning: Clear scope definition with acceptance criteria, API contracts, and security requirements
  2. Prompt Generation: Individual prompts created for each feature/component, specifying inputs, expected outputs, and constraints
  3. Antigravity Execution: AI agent (Antigravity/Claude Haiku) processes prompt and generates production-ready code
  4. Code Review: Full codebase review before moving to next phase; refactor if needed
  5. Testing: Manual testing on application + automated test file generation for each API endpoint
  6. Iteration: Refinement based on testing results; move to next phase only when phase is stable

Testing Strategy

Unit & Integration Tests: Each API endpoint has a corresponding test file covering nominal paths, error cases, and edge cases.

Manual End-to-End Testing: Features tested in the running application before release; user interactions validated against API behavior.

Antigravity Test Generation: Prompted AI agent to create comprehensive test suites for each phase; ensures rapid feedback loop and regression prevention.

02
File Ingestion Pipeline
Upload → parse → chunk → embed → index into pgvector with live status updates
Data Pipeline
Processing Pipeline
1
Upload & Validate
Magic byte validation (not extension). Max 50MB. MIME: PDF, CSV, JSON, TXT, LOG. Storage key: workspaces/{id}/files/{cuid}.ext
2
Parse (file-type aware)
PDF → pdf-parse (text + page count). CSV → papaparse (50-row blocks). JSON → key-path flattening. LOG → 2-minute time window grouping
3
Chunk
512 token max per chunk, 64-token overlap. Splits on sentence boundaries (. / \n\n). Token count ≈ len / 4
4
Embed
Model: openai/text-embedding-3-small via OpenRouter. Batches of 100 chunks. 3× exponential backoff (1s → 2s → 4s). 1536-dimensional vectors
5
Index into pgvector
Raw SQL insert via db.$executeRaw (Prisma doesn't support vector writes natively). Batches of 50 rows. HNSW cosine index for retrieval
Supported File Types
  • PDF — text extraction, page count metadata
  • CSV — column headers extracted, row-group blocks
  • JSON — deep key-path flattening to text segments
  • TXT — raw text passthrough
  • LOG — ISO timestamp detection, 2-min window grouping
API Endpoints
  • POST/api/workspaces/[id]/files

Security

Security Architecture

Security is enforced at every layer — never trusted from the client, always validated server-side.

🔐
No DB calls in frontend. All data access via typed API route handlers only.
🪪
Clerk JWT validated server-side on every protected route via requireAuth().
🏢
Workspace RBAC enforced in API middleware. Role hierarchy: OWNER > ADMIN > USER. Never trusted from client.
⚡
Rate limiting on all AI and upload endpoints via Upstash Redis sliding window limiter.
✅
Zod validation on all API inputs. Malformed requests rejected at the boundary with a 400 error.
💉
SQL injection impossible by design. Prisma parameterised queries only. pgvector raw queries use $queryRaw template literals.
📁
File uploads validated by magic bytes, not extension or Content-Type header. Storage keys derived from cuid — never user filenames.
🔗
Signed URLs for all file access. Bucket is never public. URLs expire in 1 hour.
🤖
System prompt is server-side only. OpenRouter API key has no NEXT_PUBLIC_ prefix — never exposed to client.
🪝
Clerk webhook signature validated with svix before processing. Returns 400 on invalid signature.
👑
Last OWNER protected. Cannot remove the last workspace owner. Owners cannot remove themselves.
🌐
Environment validated at startup via Zod. App refuses to start with missing or malformed config.
💬
Conversation ownership validated. conversationId verified to belong to authenticated user's workspace before message access.
🛡️
Processing errors never leak stack traces to client. Error message stored in DB, generic response returned.
📋
Source citations contain only chunkId, fileId, fileName — never raw chunk content in the citation object.
🗂️
Service worker caches GET responses only. Auth tokens scrubbed from IndexedDB before storage.
